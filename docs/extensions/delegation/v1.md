# A2A Delegation Extension, v1

**Extension URI:** `https://github.com/bkwalsh/a2a-delegation/blob/main/docs/extensions/delegation/v1.md`

**Status:** Draft

## 1. Problem

A2A authenticates each HTTP request on its own. The protocol payload carries no
identity, so a request cannot say "agent B is acting for agent A, which is
acting for user X". In a multi-hop system (user → A → B → C) each hop either
reuses a powerful credential or authenticates as itself, and the downstream
agent cannot see whose authority it is exercising. This is the setup for the
confused-deputy problem.

This extension carries a **verifiable delegation chain** on every A2A request
and guarantees that **authority can only shrink** along the chain.

## 2. Overview

1. The user authenticates once and the Security Token Service (STS) issues a
   *root token* to the first agent: `sub` = user, `aud` = that agent.
2. Before calling another agent, the caller *exchanges* the token it received
   for a new one with OAuth 2.0 Token Exchange ([RFC 8693]). The new token
   names the next agent as its audience, records the caller in the `act`
   chain, and carries the same or fewer scopes.
3. The receiving agent verifies the token, checks the chain against its
   declared policy, and authorizes each skill against the token's scopes.
   All of this happens in middleware, **before any model sees the request**.

```
 user ──login──▶ STS ──root token (aud=A)──▶ A
                  ▲                          │ exchange: subject=root, actor=A, audience=B
                  └──────────────────────────┘
                  STS ──token (aud=B, act={A})──▶ B
                                                 │ exchange: subject=…, actor=B, audience=C
                  STS ──token (aud=C, act={B,{A}})──▶ C   (depth 2)
```

## 3. Agent Card declaration

An agent that requires delegation adds the extension to
`AgentCard.capabilities.extensions` with `required: true`:

```json
{
  "uri": "https://github.com/bkwalsh/a2a-delegation/blob/main/docs/extensions/delegation/v1.md",
  "required": true,
  "params": {
    "issuer": "https://sts.example.com",
    "token_endpoint": "https://sts.example.com/token",
    "jwks_uri": "https://sts.example.com/.well-known/jwks.json",
    "audience": "agent:payments",
    "max_chain_depth": 2,
    "skill_scopes": { "refund": ["payments:refund"], "balance": ["payments:read"] },
    "trusted_actors": ["agent:orchestrator", "agent:travel"],
    "dpop_required": false
  }
}
```

| Param | Required | Meaning |
|---|---|---|
| `issuer` | yes | The only `iss` this agent accepts. |
| `token_endpoint` | yes | Where callers perform the token exchange. |
| `jwks_uri` | yes | The issuer's signing keys. MUST be HTTPS in production. |
| `audience` | yes | The exact `aud` value this agent accepts. |
| `max_chain_depth` | yes | The maximum number of `act` levels (0 = only direct root tokens). |
| `skill_scopes` | yes | Map from skill id to the scopes required to invoke it. |
| `trusted_actors` | no | If present, every actor in the chain MUST be in this list. |
| `dpop_required` | no | If `true`, tokens MUST be sender-constrained with DPoP ([RFC 9449]), see §8. Default `false`. |

## 4. Delegation token

A JWT signed by the issuer. The only accepted algorithm is `ES256`.

| Claim | Meaning |
|---|---|
| `iss` | The STS. |
| `sub` | The principal on whose behalf the request is made (usually the end user). It never changes along the chain. |
| `aud` | A single string: the agent this token is for. |
| `scope` | Space-separated scopes. Always a subset of the token it was exchanged from. |
| `act` | The delegation chain ([RFC 8693 §4.1]). The outermost `act.sub` is the agent that made this request, and nested `act` objects are earlier hops. Absent on root tokens. |
| `exp`, `iat`, `jti` | Lifetime and unique id. `exp` never exceeds the `exp` of the subject token. |
| `cnf.jkt` | Present when the token is DPoP-bound (§8). |

**Chain depth** is the number of `act` levels: 0 for a root token, 1 after one
exchange, and so on.

## 5. Token exchange (STS)

`POST {token_endpoint}`, `application/x-www-form-urlencoded`, per RFC 8693:

| Field | Value |
|---|---|
| `grant_type` | `urn:ietf:params:oauth:grant-type:token-exchange` |
| `subject_token` | The delegation token the caller received |
| `subject_token_type` | `urn:ietf:params:oauth:token-type:access_token` |
| `audience` | The target agent's `audience` |
| `scope` | Requested scopes (optional; defaults to the subject's scopes, narrowed to what the audience accepts) |

The caller authenticates as itself with exactly one client authentication
method: `private_key_jwt` ([RFC 7523] §2.2, RECOMMENDED) or a client secret
via HTTP Basic (RFC 6749 §2.3.1). A client assertion MUST be ES256-signed by
the agent's registered key, with `iss` = `sub` = the agent id, `aud` = the
public token endpoint URL, a lifetime of at most 5 minutes, and a `jti` that
the STS has not seen before. The STS MUST:

1. Verify the subject token (signature, issuer, expiry).
2. Require that **the authenticated caller is the subject token's `aud`**.
   An agent may only re-delegate authority that was delegated *to it*, so a
   token that leaks to another agent cannot be exchanged.
3. Reject any requested scope that the subject token does not hold
   (`invalid_scope`). Scopes never widen.
4. Intersect the result with the scopes the target audience accepts.
5. Reject if the new depth would exceed the STS's maximum depth.
   Also reject a target equal to the caller, and any exchange where the
   caller or the target already appears in the chain (no cycles).
6. Issue a token with the same `sub`, `aud` = target,
   `act = {"sub": caller, "act": <subject act>}`, and
   `exp = min(now + ttl, subject exp)`.

How the end user authenticates to obtain the root token is out of scope.
Any OIDC login works.

## 6. Receiving agent processing rules

For every A2A request except fetching the public Agent Card, the agent MUST
perform these checks **in order, before invoking the agent executor**:

1. The request activates the extension: the `A2A-Extensions` header contains
   this extension's URI. Otherwise reject with `extension_not_activated`.
2. An `Authorization: Bearer <token>` header is present (`DPoP <token>` when
   `dpop_required`). Otherwise reject with `missing_token`.
3. The signature verifies against `jwks_uri`, with `ES256` only.
4. `iss` equals the declared `issuer`, and `aud` equals the declared `audience`.
5. The token is within `exp`/`iat`, allowing at most 60 seconds of clock skew.
6. The chain depth is ≤ `max_chain_depth`.
7. If `trusted_actors` is declared, every `act.sub` in the chain is listed.
8. If `dpop_required`, the DPoP proof is valid and bound to the token (§8).
9. The token holds at least one scope listed in `skill_scopes`. A token that
   cannot invoke any skill is rejected up front.

Before performing a specific skill, the executor MUST check that the token holds
**all** of that skill's `skill_scopes`. This check is code, not model output:
a prompt that convinces the model to "issue a refund" still fails if the token
lacks `payments:refund`.

The verified principal is exposed to the executor as
`ServerCallContext.user`, with `user_name` set to `sub`, so tasks are owned
by the end user and not by the last agent in the chain.

## 7. Errors

Authentication failures return **401** with
`WWW-Authenticate: Bearer error="invalid_token", error_description="<code>"`.
Authorization failures return **403** with `error="insufficient_scope"`.

| Code | HTTP | Cause |
|---|---|---|
| `extension_not_activated` | 400 | The request did not activate the extension |
| `missing_token` | 401 | No delegation token |
| `invalid_token` | 401 | Malformed token, bad signature, or disallowed algorithm |
| `wrong_issuer` | 401 | `iss` mismatch |
| `wrong_audience` | 401 | `aud` is not this agent (for example, a token replayed from another hop) |
| `expired` | 401 | Token expired or not yet valid |
| `invalid_dpop_proof` | 401 | DPoP proof missing, invalid, replayed, or not bound to the token |
| `chain_too_deep` | 403 | Depth exceeds `max_chain_depth` |
| `untrusted_actor` | 403 | An actor in the chain is not in `trusted_actors` |
| `insufficient_scope` | 403 | The token lacks the scopes for the agent or the skill |

## 8. Sender-constrained tokens (DPoP)

Bearer tokens can be replayed by anyone who steals them. When
`dpop_required` is `true`:

- Each agent holds an asymmetric key pair. When it calls the token endpoint it
  sends a DPoP proof, and the STS binds the issued token to that key
  (`cnf.jkt` = the [RFC 7638] thumbprint of the public key).
- Each A2A request carries `Authorization: DPoP <token>` and a `DPoP` header
  holding a proof JWT signed with the same key, with `htm`/`htu` (the HTTP
  method and URL), `iat`, a unique `jti`, and `ath` (a hash of the token).
- The receiver verifies the proof signature, checks that the key's thumbprint
  equals `cnf.jkt`, checks `htm`/`htu`/`ath`, requires `iat` to be fresh, and
  **rejects any `jti` it has already seen** (replay protection). `htu` is
  compared after RFC 3986 normalization (lower-case scheme and host, default
  port dropped, empty path = `/`, no query or fragment).
- A DPoP-bound token MUST NOT be accepted with the `Bearer` scheme, even by an
  agent that does not set `dpop_required`.
- **Binding is per hop.** A token addressed to agent B is bound to the key of
  the caller A that presents it. When B exchanges it, B proves possession of
  *its own* key and the new token is bound to B. B is never required to hold
  A's key; the exchange is protected by rule 2 of §5 (only the audience may
  exchange) and by B's client authentication.
- The replay cache must be shared by all replicas of an agent or STS (the
  reference implementation offers an atomic Redis `SET NX EX` store); a
  per-process cache only protects a single instance.
- `htu` and the client assertion `aud` refer to the **public** URL. Behind a
  proxy, configure that URL explicitly rather than trusting forwarded
  headers.

## 9. Audit

Receivers SHOULD log one structured record per decision with: `decision`,
`code`, `sub`, the actor chain, `aud`, scopes, `jti`, and the A2A method.
Tokens and proofs MUST NOT be logged.

## 10. Security considerations

- **Enforcement stays outside the model.** Tokens, chains and scopes are
  handled in headers and middleware. The executor receives only the verified
  principal, never the raw token as message content.
- **Audience binding plus exchange-only-by-audience** stops a token stolen at
  one hop from being used against another agent or re-exchanged.
- **Monotonic narrowing**: scopes and lifetime can only shrink at each hop.
- **Bearer replay** within a token's lifetime is possible unless DPoP is
  required (the demo shows both cases). Keep TTLs short (the reference STS
  defaults to 5 minutes).
- **Key distribution**: receivers MUST fetch `jwks_uri` over HTTPS and SHOULD
  cache it with a bounded lifetime.
